# lumina-deck-pro — instructions for coding agents

Read this before writing code. It describes how this repo is built and the
handful of rules that are expensive to get wrong.

**Setting the project up is not here.** Which accounts to create, which keys go
where, how to connect Clerk to Supabase and how to apply the schema are all in
[README.md](README.md), step by step. This file assumes the app already runs —
if a command here fails on a missing key or a permission error, the answer is in
the README's troubleshooting table, not in this document. Keep the two in step:
a change that alters what a newcomer must configure — a new required env var, a
new dashboard setting, a new bucket — belongs in the README in the same commit.

## What this is

An AI presentation generator. A user describes a deck; a pipeline of agents
researches, outlines, writes, styles and illustrates it; the result is stored in
Supabase and rendered by a Next.js app.

Stack: **Next.js 16 (App Router) · React 19 · TypeScript · Tailwind v4 ·
Clerk (auth) · Supabase (Postgres + Storage + pgvector) · OpenRouter** for all
model calls.

## The one thing to understand first

**Clerk owns identity; Supabase verifies Clerk's token and enforces RLS.**

Supabase is configured with Clerk as a third-party auth provider, so a signed-in
request carries a Clerk session token that Postgres itself validates. Two
consequences that shape every line of data code:

1. **A Clerk user id is TEXT, not a uuid** — `user_2abc...`. Every `owner_id`
   column and `profiles.id` is `text`. There are no foreign keys to a users
   table, because the users table lives at Clerk.
2. **`auth.uid()` does not work.** It casts the `sub` claim to uuid, which Clerk
   ids are not. Use `public.clerk_user_id()` in every policy and function.

RLS is a genuine boundary here, and `src/lib/data/*.ts` *also* filters by owner.
Keep both — a policy mistake and a code mistake must both happen before anything
leaks.

Clerk app: `lumina-deck-pro` (`app_3IVEsae3CxcEhH0r7WP7HY047VV`), instance
domain `prime-lionfish-8591.clerk.accounts.dev`. That domain must match the
third-party auth setting in `supabase/config.toml` and in the hosted project's
dashboard, or every authenticated query fails.

## Auth rules

- Every page, Server Action and Route Handler that touches user data starts with
  `await requireUserId()` (or `requireUserIdOrThrow()` in a route handler).
- `await auth()` is **async** — a missing `await` yields `undefined` userId.
- **The proxy is a deny-list of PUBLIC routes, not an allow-list of protected
  ones.** `isPublicRoute` names what may be reached without a session and
  everything else calls `auth.protect()`, so a new route is protected the
  moment it exists rather than the moment someone remembers to add it to a
  matcher. Public today: `/`, `/sign-in`, `/sign-up`, `/api/webhooks(.*)` — and
  a future shared-deck viewer (`/d/<id>`) belongs there too, or link-shared
  decks will demand a login and the `visibility in ('public', 'unlisted')` RLS
  policies stay unreachable.
- **`/` has no landing page, on purpose.** The product is delivered to
  invited schools, so a visitor goes straight to sign-in: `src/app/page.tsx`
  redirects a signed-in visitor to `/app` and everyone else to `/sign-in`
  (which links to sign-up). `/` stays in the public list so that redirect, not
  `auth.protect()`, decides where a visitor lands. Do not re-add a marketing
  page here without being asked.
- **Clerk's webhook is how an account ends.** `/api/webhooks/clerk` handles
  `user.created` (provision the profile) and `user.deleted` (`purgeAccount` —
  storage objects first, then decks, documents, imports and the profile row).
  `user.deleted` has no backstop and cannot have one: once the Clerk user is
  gone there is no session left to delete their rows with, and nothing else
  will ever notice them again. Every handler verifies with `verifyWebhook`
  (`CLERK_WEBHOOK_SIGNING_SECRET`) — unverified, it is an endpoint that deletes
  any account whose id is posted to it — and both handlers are idempotent,
  because Svix retries anything that is not 2xx for a day.
  - It runs on the **service-role** client, and that is not a shortcut: a
    webhook arrives with no session, so `public.clerk_user_id()` is null and
    every policy would refuse. This is the background-worker case
    `createAdminClient()` exists for.
  - `ensureProfile` stays the thing the app depends on. Webhooks are
    eventually consistent, and "your account exists" is not something to make a
    new user wait on a retry schedule for. It **reads before it writes** — as
    an unconditional upsert it was a row lock, a WAL record and an
    `updated_at` trigger on every visit to `/app`, forever, to keep an
    unchanged row unchanged.
- `src/proxy.ts` is the outer gate. Its matcher must keep `'/(api|trpc)(.*)'`
  and `'/__clerk/:path*'`, and it is not a check you may rely on alone.
- In `next dev`, the first request to a route after the proxy recompiles can
  return a spurious 404. It is a compile-window artifact — verify routing
  against `npm run build && npm run start` before chasing it.
- `ClerkProvider` goes inside `<body>`, never wrapping `<html>`.
- Server code imports from `@clerk/nextjs/server`; Client Components use hooks
  from `@clerk/nextjs`. Never mix them.
- `userId` always comes from the session. If it arrives in a request body or a
  route param, it is untrusted input — ignore it.
- Clerk profile data (email, name, avatar) is read from `currentUser()`, not
  mirrored into `profiles`. Mirrored copies go stale silently.

## Next.js 16 specifics

This version differs from most training data. `node_modules/next/dist/docs/` is
the authority — read the relevant page before using an API you are unsure of.

- **Middleware is called Proxy.** One `src/proxy.ts`. There is no
  `middleware.ts` here and adding one does nothing.
- `cookies()`, `headers()`, `params` and `searchParams` are **async**.
- Default to Server Components. `'use client'` only for interactivity.
- Do not use `runtime = 'edge'`. Node.js (Fluid Compute) is the default and
  supports streaming and SSE.

## Database workflow

The schema lives in `supabase/migrations/` and nowhere else.

- **Never edit a migration that has been applied anywhere.** Write a new one.
  `npm run db:diff -- <name>` scaffolds it, or hand-write
  `<UTC timestamp>_<snake_case_name>.sql`.
- Never change schema through the dashboard SQL editor without capturing it as a
  migration. Dashboard-only changes are silently reverted by the next push.
- New tables get `enable row level security` **and** policies in the same
  migration — owner policies keyed on `public.clerk_user_id()`, or
  `public.is_deck_owner(deck_id)` for anything hanging off a deck.
- After any schema change: apply it, run `npm run db:types`, and commit the
  regenerated `database.types.ts` with the migration. Add any new convenience
  alias to `src/lib/supabase/types.ts`, not to the generated file.
- A `language sql` function body is parsed at CREATE time, so it cannot
  reference a table defined in a later migration (`is_deck_owner` lives in 0300
  with `decks` for exactly this reason). `language plpgsql` defers the parse.

```bash
npm run db:start   # local Postgres via Docker
npm run db:reset   # drop, re-run every migration, then seed.sql
npm run db:link    # link to the hosted project (once)
npm run db:push    # apply pending migrations to the linked project
npm run db:types   # regenerate database.types.ts
```

### Tables

| Table | Purpose |
|---|---|
| `profiles` | keyed by Clerk user id; generation preferences only |
| `decks` | one row per deck: prompt, status, visibility, extracted `style_spec` |
| `slides` | ordered content, `blocks` jsonb — never rendered HTML |
| `deck_assets` | generated/uploaded images, keyed to bucket + path |
| `generation_jobs` | one per build; readable by the owner over Realtime |
| `agent_runs` | one per agent stage: model, tokens, cost, latency, raw output |
| `documents` / `document_chunks` | RAG corpus; `vector(1536)` + HNSW cosine index |
| `deck_drafts` | the outline awaiting review, and the chat about it |
| `deck_imports` | an uploaded .pptx/.pdf/.docx being parsed into a deck |
| `deck_exports` | a .pptx/.pdf/.png_zip rendered from a deck, regenerable |

Buckets: `deck-assets` (public) and `deck-uploads` (private). **Every storage
path starts with the deck id** — `<deck_id>/<filename>` — because the storage
policies authorise on that first segment. Any other shape is rejected.

## Generation flow

```
create-deck-dialog → createDeckAction → after(runDeckDraft)      ~$0.011
                          ↓                     ↓
        deck row + template or reference   research → outline
                                                ↓
                                     deck_drafts + status='awaiting_review'
                                                ↓
                              ┌──── DraftReview (/app/decks/<id>) ────┐
                              │   reviseDraftAction ⟲  (~$0.001/turn) │
                              └──── approveDraftAction ───────────────┘
                                                ↓
                          after(runApprovedBuild)                     ~$0.24
                                                ↓
  DeckCard ← Realtime+poll ← generation_jobs ← reportProgress ← Manager (Agents/)
                                                ↓
                          slides + deck.style_spec + deck-exports/<deck_id>/<id>.pptx
```

**The build stops for a person after the outline.** That split is about money,
not ceremony: research and planning cost about a cent, and everything after
them costs twenty to thirty times that — almost all of it illustration. A user
who wanted a different deck used to find out only once the whole thing had been
paid for. `Manager.draft()` returns the ResearchBrief and the ContentPlan and
stops; `Manager.buildApproved()` re-enters at the style analysis with a plan a
person has said yes to, so nothing is researched or planned twice.

`revisePlan()` is the chat: one call to the same specialist that wrote the
plan, handed the plan AND the research it came from, returning a complete
replacement rather than a patch. Passing the research is what stops "add a
slide on cost" being answered with an invented figure — a revision can only use
facts the Researcher actually found, or say it cannot.

`Agents/cost.ts` prices the build from **measured** per-call costs so the
approval screen can state a number. Re-measure it with `npm run smoke:deck`
whenever the model table below changes: a rate card is not a cost, because
reasoning tokens bill as output and a cheap model that thinks for eighty
seconds is an expensive one.

Inside the Manager the stages run in a **strict sequence**, each consuming the
one before it:

```
  research  →  outline  →  style  →  write  →  illustrate  →  font + build  →  QA
      │           │          │         │           │              │            │
 ResearchBrief ContentPlan StyleSpec SlideSpec[] images      Google Fonts   revise?
```

Nothing here runs concurrently, and that is the point: facts have to exist
before a narrative can select from them, the narrative before slides can be
written to a word budget, the StyleSpec before an image can be generated in the
deck's look. Two of these in parallel means the second is working from an
assumption rather than a result.

- **Research is the only stage allowed to introduce facts.** `researcher.md`
  reads whatever is in `Documents/` via the `read_document` tool (pdf, docx,
  txt, md, csv, json, html), and when there is nothing to read the call is made
  with **live web search attached** — OpenRouter's `web` plugin, engine
  `native`, which on a Gemini model is Google Search. No separate search key:
  the search is billed through the same call. Every finding carries a
  confidence grade and a source kind (`document` / `web` / `model-knowledge`),
  and what could not be established goes in `openQuestions` rather than being
  quietly filled in.
- **Word budgets are a RANGE, set at planning time and counted in code.** Each
  ContentPlan slide carries a `section` (`intro` / `body` / `conclusion`, so
  every deck opens and closes — `normalisePlan` repairs a plan that forgot) and
  a `wordBudget` covering all visible copy. `check_word_budget` counts the
  actual words after design.
  - **Over**: a small overage is a `major` QA issue, more than 25% over is
    `critical`. Speaker notes are excluded on purpose — they are where detail
    is meant to go when a slide is over.
  - **Under `MIN_BUDGET_USE` (50%)**: also a `major` issue, and the one that
    was missing. A ceiling on its own produces the opposite failure from the
    one it prevents: a designer that writes "Following a recipe" in each of
    three cards is comfortably inside 60 words and has said nothing. Three
    labels is not a slide, it is a list of headings — and it measures as
    exactly that, so code can say so rather than leaving it to taste. Title
    slides are exempt; being brief is their job.

  The default ceiling is **55** words. It was 85, set when the worry was
  slides of bare labels; `MIN_BUDGET_USE` now guards that end of the range, so
  the ceiling came down to what a person can read off a projected slide. Every
  slide is guaranteed a picture and the picture takes the larger share of a
  hero layout (`HERO_IMAGE_SHARE`, 0.55) — which only pays off if the copy
  beside it is short. The prompts ask for "the thing, then what makes it
  matter" in 6-14 words per bullet, two or three bullets to a slide.
- **Every slide gets a picture, and that is guaranteed in code.** The Slide
  Designer is told to put an `image` element on every slide and usually does;
  `ensureSlideVisuals` makes it true either way. Where a slide has room,
  `largestFreeRect` finds the biggest genuinely empty rectangle and puts an
  illustration in it — exact rather than heuristic, because "the right half is
  free" is true of a two-column layout and false of every other one, and being
  wrong means a picture on top of the body copy. Where a slide has no room, it
  gets a generated backdrop instead, dimmed harder than usual because the copy
  over it needs the contrast. A deck where four slides are illustrated and two
  are walls of text does not read as designed; it reads as a deck that ran out
  of budget.
- **The model chooses the shape of a slide; code computes the rectangles.**
  The Slide Designer sets an `archetype` (`title-hero`, `hero-right`,
  `three-column`, `stat-row`, `quote`, `full-bleed`, …) and gives each element
  a `slot`; `applyLayouts` replaces the box with the rectangle `slotsFor`
  derives from that archetype and the deck's own canvas, margins and type
  sizes. The designer's `box` values are placeholders.

  This is the single highest-leverage thing in the pipeline and it is not a
  taste call. On PPTBench (4,439 samples from 958 real decks) GPT-4o scores
  94% understanding a slide and **30% generating one**; handing it a layout
  instead of a blank canvas takes generation to 46%, and Gemini-2.0-Flash from
  38% to 56%. Every system that produces good decks arranges for the model not
  to be the last thing that touches geometry — PPTAgent inherits it from a
  human-made slide, AutoPresent hides it behind semantic calls, Kimi's PPTD
  skill checks it against a rendering. Overlapping boxes, a card squeezed to
  nothing and an element off the canvas are all the same failure, and it is a
  failure of arithmetic done by eye.

  An archetype is deliberately *not* a template in the Canva sense, and it is
  not the same thing as a **deck template** (`src/lib/templates.ts`, which is a
  StyleSpec). The rectangles are derived from whatever StyleSpec the deck has,
  so two decks get different geometry from the same archetype whether their
  design systems came from two reference images or two templates. The look
  comes from the StyleSpec; only the arithmetic is fixed. `npm run smoke`
  asserts that every archetype's slots are in bounds and mutually disjoint,
  which is the property the whole module exists for.

  A slide with no archetype keeps the designer's boxes, so this is additive —
  and `fitToCanvas` / `growTextBoxes` / `ensureSlideVisuals` still run over
  both kinds, just with far less to do on a slotted one.
- **A slot may be claimed by more than one element, and it is divided, not
  shared.** The Slide Designer is asked to head each group of bullets with a
  short label, so a `three-column` slide legitimately arrives with a `label`
  and a bulleted `body` both slotted `col-1`. Giving each of them the slot's
  rectangle drew them on top of each other — the same words in the same pixels,
  which is the exact failure archetypes exist to prevent. `stackInSlot` splits
  the slot vertically instead, each element getting the room its own text needs
  and the last one absorbing the slack. Three later passes have to know this:
  `compactColumnCards` measures a column as the SUM of its stack and re-stacks
  the row, `compactTitleBand` moves a whole stack up but grows only its lowest
  member, and `SlideCanvas`'s export grid wraps co-slotted elements in one flex
  column (two children of one `grid-area` occupy the same cell, which is an
  overlap, not a stack). `npm run smoke` asserts the split is in-bounds and
  disjoint for every slot of every archetype; `npm run smoke:render` builds the
  reported slide and asserts no two text boxes on it share a pixel.
- **Geometry is corrected, never litigated — including type.** `fitToCanvas`
  slides an out-of-bounds box back on, and `growTextBoxes` grows a box that is
  too short for its own text downward into free space. Both exist for the same
  reason: a designer working in inches gives a two-line heading a one-line box
  often enough that treating it as a QA failure buys a revision round — at
  roughly the price of the whole rest of the build — to fix a number the
  pipeline can compute itself.
- **The deck is looked at before it ships.** `rasterizeSlides` draws every
  slide to a PNG and `contactSheet` puts them on one sheet;
  `reviewLayoutVisually` sends that to `OPENROUTER_VISION_MODEL` with a
  checklist of things a picture reveals — text off the edge, a title on
  someone's face, one illustration in a different style from the rest, a slide
  emptier than its neighbours, lettering rendered *inside* a generated image.
  Every other check in this pipeline reads the spec and is therefore blind;
  this is the only one that can fail for a reason nobody wrote a rule for, and
  it costs about a third of a cent.

  **The rasteriser uses glyph outlines, not a browser.** `fontkit` already
  loads the deck's real .ttf to measure it, and it exposes each glyph's path —
  so text draws as the actual letterforms of the actual typeface with no font
  installed on the machine, and the picture cannot lie about the very thing
  the check is for. A headless browser would be marginally more faithful and
  costs ~150MB plus a launch per build. `npm run smoke:render` writes the
  contact sheet out so it can be inspected: if that sheet is not legible, the
  check consuming it is worthless.

  Its findings are capped at `major` and it never fails a build — no fonts, no
  network, a model that will not answer, and the review is simply skipped.
- **Only counted facts can force a revision.** `review()` merges the technical
  validation, the layout checks (out-of-bounds and overlap are exact box
  arithmetic, so they count at `critical`; text-overflow is an estimate, so it
  stays `major`) and the word-budget count at their real severity, and caps
  the `pptx-reviewer`'s own issues at `major`. The reviewer never sees a
  rendered slide — its inputs are those same code checks — so a `critical`
  from it is inference, and it was spending a whole extra build on decks that
  code had just found nothing wrong with. Its notes still steer the Slide
  Designer when a revision does happen.
- **A revision is bounded and reuses every picture QA did not flag.**
  `MAX_REVISIONS = 1`: the reviewer is consulted at most twice total — once on
  the first build, once more on the single revision that follows if it did
  not pass — because each round is a full rebuild, and the cost of chasing a
  clean pass grows faster than the odds of getting one. `designSlides`'s
  revision prompt tells the model to fix wording, budget, geometry and colour
  in place rather than touch any `image` element, and
  `Manager.carryForwardImages` backs that with code: a revised slide gets its
  previous round's `imagePath`/`background` back by slide number before
  `illustrate` runs, so only a slide left without a picture — new, or one QA
  specifically called wrong — generates one. `Manager.collectImagePaths`,
  not an accumulator carried across rounds, is what actually gets uploaded,
  so a carried-forward image from a round that never finished still ships.
- **Fonts are chosen at build time, not with the style.** `curateFonts` runs
  immediately before `createPptx`, once per build (fonts do not depend on the
  slides, so a revision round does not re-choose them). It is the last decision
  before the file is assembled and the one that talks to a live Google Fonts
  lookup.
- **Working memory** (`Agents/memory.ts`) is how the specialists share context.
  None of them shares a conversation, so each prompt carries a `digest()` of
  what earlier stages established. It also records the trace — steps, results,
  errors, streamed reasoning and stage handoffs. It lives in a process-level
  `Map` keyed by job id and `manager.dispose()` deletes it in `runDeckGeneration`'s
  `finally`: it holds research notes, prompts and reasoning for a deck that is
  finished, and the server process outlives the request by days.

- **`deck_status` has an `awaiting_review` state**, between `draft` and
  `generating`. A deck in it has a row in `deck_drafts` and no slides, so
  `/app/decks/<id>` renders the outline instead of an empty viewer, and the
  card offers no Download or Regenerate — there is nothing yet to download.
  `clearDraft` removes the row once the build finishes: a stale outline beside
  a finished deck only invites edits that cannot take effect.
- The build runs in `after()`, not in the request. A deck takes minutes; the
  form returns immediately with the deck in `generating`, and the card follows
  the job over Realtime (`generation_jobs` is in the `supabase_realtime`
  publication and RLS-scoped to its owner, so the browser subscription is safe).
  - **`after()` is not a job queue, and the difference matters at scale.** The
    build runs inside the web process that served the form, so it is bounded by
    that function's timeout (300s on Vercel), it dies with a deploy or an
    instance recycle, it cannot be retried, and its progress is only in
    `generation_jobs` because it writes there. Below `ACCOUNT_LIMITS`, this
    holds. Beyond it the honest fix is a real worker — the job row already
    models one (`queued`/`running`, `stage`, `progress`, and a partial index
    `generation_jobs_active_idx` on exactly the live statuses, which nothing
    currently polls) so the change is a consumer, not a schema.
- **Money is rate-limited per account, and `startJob` is the chokepoint.**
  Every build in the app opens its job there — create, approve, regenerate — so
  `assertBuildQuota` sits inside it and no path can spend without asking. The
  actions call `checkBuildQuota`/`checkDeckQuota` first so a refusal lands on
  the form as a sentence rather than as a failed job on a card; that is the
  courtesy, `startJob` is the control. `src/lib/limits.ts` holds the numbers:
  two concurrent builds, 25 in a rolling 24 hours, 200 decks. They are
  constants, not env vars — a limit that can be raised by an environment
  variable gets raised during an incident and never lowered again.
  - The deck ceiling gates **creating** a deck only. Applied to builds it would
    strand an account at the limit with an outline it can never approve.
  - A failed count throws rather than passing. Refusing costs a user one build;
    passing would let a database blip switch the spend limit off.
- `runDeckGeneration` never throws. It is a fire-and-forget callback with nobody
  to catch it, so every exit path lands on the job row instead.
- `src/lib/data/generation.ts` writes on the **service-role** client, because
  `generation_jobs` and `agent_runs` are read-only to `authenticated` by design.
  `startJob` re-checks ownership on the user-scoped client first; nothing else
  in that file may be called with a deck that has not been through it.
- **A deck needs a design system before a slide can be written, and there are
  exactly two ways to get one: pick a template, or upload a reference image.**
  Neither, and `createDeckAction` refuses — the style analyzer has no fallback
  aesthetic, so the deck would be created only to fail a minute later.
  - The templates live in `src/lib/templates.ts` and each one IS a complete
    `StyleSpec`, written by hand and checked: every text/background pair clears
    WCAG AA so `readableOn` never substitutes, every size is already above
    `MIN_TYPE_SIZES` so `legibleSizes` has nothing to lift, the families are
    real Google Fonts so `font-curator` confirms rather than repairs, and
    `visualLanguage` is written as art direction because it is read verbatim
    into every image prompt for the deck.
  - A chosen template is resolved to that StyleSpec at **creation** and written
    to `decks.style_spec` — the column whose job is the deck's design system.
    It needs no new column and no lookup at build time: `openRun` reads it back
    through `styleSpecSchema`, and `source.type === 'template'` is what tells
    `Manager.analyzeStyle` to use it verbatim and make no vision call at all.
    An image deck's `style_spec` is the *analyzed* spec, so `source.type` is
    `'image'` and a rebuild re-derives it — which is what makes swapping the
    reference image actually change the deck.
  - The two are alternatives, not layers. Choosing a template does not upload
    the reference image, because nothing would ever read it.
- **Telemetry.** Every model call writes an `agent_runs` row — agent, attempt,
  model, prompt/completion tokens, cost, latency, and the raw output. It rides
  an AsyncLocalStorage sink (`Agents/telemetry.ts`) so `Agent.ts` stays ignorant
  of Supabase, job ids and deck ids. `withTelemetry` waits for in-flight sink
  writes before resolving, so `rollUpJobTotals` afterwards cannot miss a row.
  - Usage comes from `getUsage()`, never `getResponse().usage` — the latter
    covers only the final round of a multi-round call.
  - `cost_usd` is **null** when the provider reported none. Do not coalesce it
    to zero: "not reported" and "free" are different facts, and summing the
    second is a lie the deck list would repeat.
  - A schema-validation failure is recorded as a failed run with the raw text,
    even though the model answered — the pipeline could not use what came back.

## Rendering a deck in the app

The .pptx is the deliverable; the app renders the same deck in the browser
from the same specs.

```
finishJob → slides rows (blocks, hero_image_url, background_url, metadata)
                 ↓
          toDeckView(deck, slides)          src/lib/slides/deck-view.ts
                 ↓  { theme, slideSize, slides }
          <SlideCanvas>                     src/components/slides/slide-canvas.tsx
                 ↓
   DeckViewer (/app/decks/<id>)  ·  DeckCard thumbnail (/app)
```

- **`SlideCanvas` is the web half of `Agents/pptx/builder.ts`**, and the two
  *share* their rules rather than reimplementing them. `placementFor`,
  `readableOn`, `shrinkToFit`, `estimateLines`, `TEXT_SCRIM_OPACITY` and
  `MIN_BACKDROP_DIM` all live in `Agents/pptx/theme.ts` and are imported by
  both. A preview that composes a slide differently from the file the user
  downloads is worse than no preview, and two copies of a rule are two rules.
- **Alignment is decided by role and content, in one place.**
  `placementFor(type, role, content)`: prose reads left/top, a display
  statistic or a *short* card label is centred both ways. Content is part of
  the decision because centring is only comfortable for a line or two — a card
  explaining itself in twenty words is prose whatever box it sits in, and
  ragging both edges of a paragraph is the fastest way to make a slide look
  amateur. A list always reads from one left edge, however short its items. An
  element may override with `align` / `valign`, and both renderers honour it.
  Before this each renderer aligned independently and agreed by luck.
- **Type has a legible floor.** The StyleSpec's sizes come from a vision model
  reading a *picture* — a screenshot at some arbitrary scale — so a perfectly
  sensible reading lands body copy at 12pt, which on a 13.3in slide is a
  paperback footnote projected across a room. Nothing else catches it: the box
  fits, the contrast is fine, and the slide is unreadable from the third row.
  `MIN_TYPE_SIZES` (title 30, subtitle 20, body 18, caption 14) lifts the whole
  scale by one factor rather than clamping each size, so the hierarchy the
  reference image actually described survives — a deck whose body was a quarter
  of its title still is. A title is separately capped at a sixth of the slide
  height, because that end of the scale really is about the canvas.
- **Text colour is checked against what is actually behind it.** `readableOn`
  keeps the theme's intended colour when it clears WCAG AA and swaps in the
  most readable colour from the deck's own palette when it does not. "Behind
  it" is the surface colour inside a card, and the background colour on the
  slide — which is only true because of the next two rules.
  - Text laid **over a picture** gets a panel of the background colour at
    `TEXT_SCRIM_OPACITY`. A photograph is not a colour, so `readableOn` cannot
    reason about it; covering the picture where the words are gives it
    something to reason about.
  - A **generated backdrop** is floored at `MIN_BACKDROP_DIM` (0.55). The
    Background Designer picks `dim` for looks and picked 0.25 on a busy
    pattern, which leaves it at three-quarters strength under the deck's copy
    and makes "the background is the background colour" simply false. The floor
    is applied when a deck is built *and* in `toDeckView`, so decks already in
    the database are drawn correctly too.
- **Text is measured, not estimated.** `pptx/text-metrics.ts` downloads the
  deck's actual Google Font — `fontkit`, the same library pdfkit uses — and
  measures glyph advances, so line counts and wrap points are facts rather than
  a character count times a constant. That constant was wrong in both
  directions at once: Playfair Display Bold averages 0.514em per character on
  "Algorithms Around You" and far more on a line of capitals, and 5% of error
  is the difference between a heading on one line and a heading whose last word
  is silently clipped.

  The size each element is drawn at is resolved once, on the server, and stored
  on the element as `fontSize`. **Both renderers draw that number** rather than
  recomputing — which is what makes them break lines in the same places instead
  of in places that happen to agree. A font that cannot be fetched (offline, or
  a system face Google does not host) falls back to the estimate in `theme.ts`:
  worse, but not broken.

  A headless browser would be more faithful still — it would catch kerning,
  ligatures and CSS line-breaking. It also costs ~150MB and a browser launch
  per build, and the npm packages that convert HTML straight to .pptx are all
  hobby-scale (a few hundred downloads a month) and emit slides of flattened
  images rather than editable shapes. Measuring the font is 1MB and fixes the
  part that actually mattered.
- **A one-line heading gives its space back.** A slot has to be sized before
  anyone knows what will go in it, so `slotsFor` reserves two lines for every
  title — less would clip the ones that wrap. Once the font is measured the
  real height is known, so `compactTitleBand` shrinks the title box to what it
  uses and grows the content beneath it into the gap. Bottom-anchored elements
  stay anchored: a footnote belongs at the foot of the slide, not tucked under
  the content with an inch of nothing below it.
- **Overlong text is shrunk by a computed factor, not delegated.**
  `shrinkToFit` steps the size down until the text genuinely fits — stepped
  rather than solved, because the line count comes from a `ceil` and a
  closed-form ratio lands between steps and still overflows. `estimateLines`
  widens its glyph estimate for capitals, without which an uppercase heading is
  measured a quarter too narrow and runs over the subtitle beneath it. The
  The .pptx deliberately does **not** carry `fit: 'shrink'`. That writes an
  `<a:normAutofit>` flag for PowerPoint to interpret — neither pptxgenjs nor
  python-pptx computes the scale itself — so the size PowerPoint settles on is
  one `SlideCanvas` cannot reproduce. Pre-fitting in code is the only approach
  where the file and the preview can agree.
- **One component, every size.** The slide is a CSS container and all type is
  in `cqw` — a point is 1/72in and the canvas is `slideSize.width` inches, so
  `pt → cqw` is `(pt / 72 / width) * 100`. That is why the same component is
  the 1100px stage in the viewer and the 240px thumbnail on a card, with no
  size prop and no second code path.
- **A card's content may be `text` or `items`.** Both renderers read both. They
  used to read only `text`, which drew an empty rounded rectangle for every
  card a designer filled with bullets — silently, in the .pptx and the browser
  alike, with the validator passing it the whole way. `npm run smoke` now
  builds a deck containing both kinds and asserts the words are present in the
  slide XML, because a shape rendering is not evidence that anything is in it.
- **`blocks` holds URLs, not paths.** `replaceSlides` swaps each element's
  `imagePath` — an absolute path in a temp dir on the build machine — for
  `imageUrl`, the public CDN URL. Local paths are useless to a browser and
  should not be handed to one. `src/lib/slides/blocks.ts` parses the result
  back with Zod, because `jsonb` does not preserve the shape the pipeline
  validated.
- **PowerPoint has no z-index.** The builder draws in insertion order, so a
  caption written before the card it labels vanishes behind it. `layer()` sorts
  pictures, then containers, then text; `SlideCanvas` sorts by the same
  function so the two stack alike.
- **Images are keyed by path, never by position.** A build produces backdrops
  first and illustrations second; an ordered array pairs slide 3's hero with
  slide 1's backdrop. `ImageUrlMap` is `localPath → publicUrl`, which is the
  only identifier both stages agree on.
- **Elements can move, and only in the browser.** Every element carries an
  optional `motion` (`Agents/motion.ts`): an `effect` (`zoom-in` / `zoom-out` /
  `none`), an `intensity`, a duration, a delay, an easing, an origin and a
  `trigger` (`enter` / `hover` / `click`). `SlideCanvas` draws it as CSS
  custom properties against one keyframe set in `globals.css`, and **only in
  `viewportMode: 'live'` with `animate` on** — never in a thumbnail, and never
  in the headless export render, where a box caught mid-zoom would measure as
  whatever scale it happened to be at.

  The .pptx has no animations at all: `pptxgenjs` cannot write them, and the
  rule that the preview must not do things the download cannot is answered by
  making motion the one *presentational* layer that never touches a `box`.
  Every effect ends at scale 1 — the element's laid-out size — so every
  geometry pass upstream still describes what a viewer actually sees.
  `npm run smoke` asserts exactly that, in both directions and both triggers.

  **The model picks the effect; code picks the timing.** The Slide Designer
  may set `effect` and `intensity` on any element and is told to leave most
  elements alone. `Manager.ensureSlideMotion` runs last, after every geometry
  pass, and fills in the rest: the house default per element type (a heading,
  a picture and a standout number arrive; body copy does not) and the
  **stagger**, which nobody asks a model for — a model handed a timeline gives
  eight elements the same 0.3s, and a cascade is arithmetic. It runs in draw
  order and is capped at `MAX_STAGGER`, so a busy slide does not become a slow
  one. A `delay` the designer set itself is kept.

  **A person can change all of it, per element.** The viewer's Animation panel
  (`animation-editor.tsx` + `motion-stage.tsx`) selects an element from a list
  or by clicking it on the slide, edits the same `Motion` the pipeline wrote,
  previews against the real renderer, and saves through
  `updateSlideMotionAction` → `setSlideMotion`, which rewrites only the
  `motion` key of the stored block on the **Clerk-scoped** client. Edits are
  addressed by rendered index, mapped back through `parseBlocksWithIndex` —
  the stored and rendered indices diverge the moment one malformed block is
  dropped, and an edit landing one element over is invisible.

  **Present is a mode, not a class.** `present-mode.tsx` is a separate surface
  — real fullscreen where the browser allows it, a fixed black overlay
  regardless, the slide sized from the deck's own ratio so it is never
  cropped. It binds the wider key set a room needs (Space, arrows, Page
  Up/Down for a remote, Home/End, `N` for notes, Escape out) and the viewer's
  own handler stands down while it is open, or every key would advance the
  deck twice. Controls and cursor fade after `IDLE_MS` of stillness. It draws
  through the same `MotionStage` with `editing` off, so a click zooms an
  element instead of selecting it — and it presents the *edited* slides, so an
  unsaved animation is still the one you rehearse with.

  A rebuild does not keep hand-set motion: `replaceSlides` deletes and
  reinserts every slide, and there is no element identity to carry an
  animation across. Worth revisiting only if elements ever get stable ids.
- **`slide.title` is metadata and nothing draws it.** The builder composes a
  slide from `elements` alone, so a designer that fills in `title` and forgets
  the matching text element ships a deck with no headings — in the .pptx and in
  the browser. `ensureTitleElements` in the Manager draws the missing one into
  the top band (and leaves the slide alone if that band is occupied), so the
  fix lands in both outputs from one place.

### Building the file

The .pptx is produced by **`pptxgenjs`** (npm, v4), driven by
`Agents/pptx/builder.ts`. Nothing here hand-writes OOXML: the builder reads a
`SlideSpec[]` and a theme and calls `addText` / `addShape` / `addImage`, which
is what keeps it deterministic and testable without a model in the loop.
`npm run smoke` builds a real deck and validates it on every run.

`Agents/tools/validate-pptx.ts` then opens the written file and checks it is a
readable archive with the expected slide count — a build that produced a
corrupt file must fail loudly rather than reach a user's Downloads folder.

## Security rules

1. **The service-role client bypasses RLS.** `createAdminClient()` is for
   background workers with no session. In request paths use the Clerk-scoped
   client from `@/lib/supabase/server` — it is not more work and it fails safe.
2. Never prefix a secret with `NEXT_PUBLIC_`. `CLERK_SECRET_KEY` in particular
   never appears in client code.
3. `match_document_chunks` is `security invoker` — RLS scopes it. Do not
   "fix" a permission error by making it `security definer`.
4. Treat model output as untrusted input: validate its shape before it reaches
   the database, and never interpolate it into SQL.
5. Re-check ownership server-side even when the UI already hides the control.

## Model calls

- All text and image generation goes through OpenRouter, configured by env.
  Model slugs are never hardcoded — providers retire them, and env is where
  they change.

  | Var | Default | Used by |
  |---|---|---|
  | `OPENROUTER_MODEL` | `z-ai/glm-5.3-flash` | fallback for a skill that doesn't pick its own |
  | `OPENROUTER_VISION_MODEL` | `google/gemini-3.6-flash` | the style-reference → StyleSpec conversion |
  | `OPENROUTER_IMAGE_MODEL` | `google/gemini-3.1-flash-lite-image` | illustration generation (`Agents/images.ts`) |
  | `OPENROUTER_IMAGE_TIER` | `on` | `off` disables illustration generation |
  | `OPENROUTER_IMAGE_PALETTE` | `0.7` | how far images are pulled into the deck's palette, 0-1 |
  | `OPENROUTER_VISUAL_REVIEW` | `on` | `off` skips the rendered-deck vision check |
  | `OPENROUTER_REASONING_EFFORT` | `medium` | every call; `minimal` also empties the trace |
  | `OPENROUTER_SEARCH_ENGINE` | `native` | the Researcher's web search |
  | `OPENROUTER_SEARCH_MAX_RESULTS` | `8` | results per research call |
  | `OPENROUTER_SEARCH_TIER` | `on` | `off` forbids reaching the web |

- **Every agent names its own model, and every one is a small one.** The
  pipeline is multi-model by design: each specialist declares a `model:` line in
  its Markdown frontmatter, so the choice sits next to the prompt it belongs to.

  | Specialist | Model | measured $/call |
  |---|---|---|
  | `researcher` | `google/gemini-3.6-flash` | re-measure with `npm run smoke:deck` |
  | `style-analyzer` | `google/gemini-3.6-flash` | re-measure with `npm run smoke:deck` |
  | `content-planner` | `z-ai/glm-5.3-flash` | 0.0007 |
  | `slide-designer` | `z-ai/glm-5.3-flash` | 0.0007 |
  | `background-designer` | `z-ai/glm-5.3-flash` | 0.0002 |
  | `font-curator` | `z-ai/glm-5.3-flash` | 0.0002 |
  | `pptx-reviewer` | `google/gemini-3.6-flash` | re-measure with `npm run smoke:deck` |

  All of them reason and all of them are small, which is the right trade here:
  the work is structured judgement over a short context, not open-ended
  generation, and a frontier model at 10-40x the rate did not produce a better
  deck. The two Gemini stages are Gemini on purpose — the Researcher's
  `engine: native` search is Google Search only on a Google model, and the
  style analyzer has to actually look at an image.

  **Pick a model on cost per call, never on the advertised rate.** Reasoning
  tokens are billed as output, so a model with a low rate that thinks for
  thirty thousand characters is expensive. `deepseek/deepseek-v4-flash` has the
  lowest sticker price of anything here — $0.168/1M out — and measured **38x
  more per call** than `glm-5.3-flash` on the same prompt, because it spent 80
  seconds thinking about it. `npm run smoke:deck` prints the per-call cost of
  every stage; that number is the one to optimise.

  The text pipeline totals **~1.5 cents** for a six-slide deck. Illustration is
  the rest of the bill by an order of magnitude — five images at ~$0.034 each —
  so `OPENROUTER_IMAGE_TIER=off` is the real cost switch, not the model table.

  `OPENROUTER_MODEL_<SKILL>` (e.g. `OPENROUTER_MODEL_SLIDE_DESIGNER`) overrides
  the frontmatter, because a retired slug must be fixable without editing a
  skill file — and because raising one disappointing stage should not mean
  raising the whole pipeline:

  ```markdown
  ---
  model: google/gemini-3.6-flash
  ---
  [ROLE / AGENT DESCRIPTION]
  ```

  The value must be a `provider/model[:variant]` slug or `loadSkill` throws.
  All eight specialists declare one; `OPENROUTER_MODEL` is only the fallback for
  a skill that does not.
- **The frontier image model is not worth it.** Measured on the same prompt:
  `gemini-3.1-flash-lite-image` $0.034, `gemini-3.1-flash-image` $0.068,
  `gemini-3-pro-image` $0.139 — and the most expensive produced the *least*
  legible illustration of the three. Quality here comes from the art direction
  in `image-prompt.ts`, not from the model tier. Illustration is still ~90% of
  a deck's bill, so `OPENROUTER_IMAGE_TIER=off` remains the real cost switch.
- **Resolution is capped by the model, so stop pretending otherwise.** Every
  image model measured returns about a megapixel whatever pixel count the
  prompt asks for; they honour the aspect ratio and ignore the rest. The old
  code resized to the request anyway, which enlarged a 976px image to 1280px —
  softer than what the model drew and larger on disk for the privilege.
  `targetSize` now honours the box's ratio exactly and never enlarges.
- **The palette is enforced, not requested.** The style block asks for the
  deck's colours and forbids the rest, and that holds until the subject has a
  conventional colour: ask for a pond in a navy-and-amber deck and you get
  green, every time, because a negative instruction is the weakest kind there
  is. `Agents/palette.ts` maps each pixel's brightness through a ramp built
  from the deck's own palette and blends it back at `OPENROUTER_IMAGE_PALETTE`
  (0.7). Luminance is preserved, so form, shading and detail survive while
  stray hues are pulled into the family. Deterministic, and free — no model, no
  second call.
- **Image generation is a TOOL, not an agent.** `generate_image` sits in the
  registry beside `check_google_font` and `analyze_style_image` — making a
  picture has no reasoning in it. Agents decide *what* a picture shows; the tool
  makes it. `background-designer` is the agent whose whole job is exactly that:
  it picks which slides deserve a generated backdrop (most do not), writes an
  abstract prompt for each, and sets a `dim` so the scrim keeps text readable.
  Its telemetry is filed under `tool:generate_image`, not as an agent run.
- The style reference image is sent to the vision model as an attached
  `data:` URL, downscaled to 1568px. Only that one stage sees the image — every
  other specialist works from the StyleSpec JSON it returns. A deck built from
  a **template** skips this stage entirely, along with `style-critic`: the
  StyleSpec is already known, so there is nothing to look at and no vision call
  to pay for.
- **Image prompts are JSON, split into a locked half and a varying half.**
  `Agents/image-prompt.ts` derives a `style` block from the StyleSpec —
  palette, visual language, treatment, principles — that is **byte-identical in
  every request for a given deck**, and pairs it with a `subject` block that is
  the only thing differing between images. Prose prompting cannot hold a house
  style across twelve slides: the same look rewritten twelve times drifts, and
  the drift is invisible until the deck is open. `styleEnvelope()` is purely
  derivative — no model, no randomness — so swapping the subject provably does
  not move the style. That is also the seam for customisation: change the
  subject and the objects, leave the style alone.
- **Geometry is corrected, not litigated.** `fitToCanvas` slides any element
  box back onto the slide before the build (`fitToSlide` in
  `Agents/pptx/positioning.ts`, sliding before shrinking so type sizes survive).
  A designer working in inches overshoots the edge by a tenth of one often
  enough that the builder's `ELEMENT_OUT_OF_BOUNDS` guard was killing whole
  decks over arithmetic. The guard stays as an invariant; this pass makes it
  unreachable.
- **Images are generated, not referenced.** The Slide Designer sets
  `imagePrompt` (what the picture SHOWS); `Agents/tools/illustrate-slides.ts`
  runs between design and build, generates each PNG at 192dpi sized to the
  element's own box, writes it to the job's temp dir and fills in `imagePath`.
  A designer cannot know a path that does not exist yet, so asking it for one
  only ever produced fiction that broke the builder — which requires a real
  file. An image that fails to generate is dropped, and if that would leave a
  slide blank its title is re-added as text: a deck missing one illustration is
  a deck, a blank page in the middle of one is a bug. Generated files are then
  uploaded to `deck-assets/<deck_id>/` and recorded on `slides.hero_image_url`
  for the web renderer.
- **Fonts are verified, not trusted.** The style analyzer can only *estimate* a
  typeface from an image, so `font-curator` resolves that estimate to a real
  Google Fonts family. `check_google_font` settles availability against
  `fonts.googleapis.com/css2` (400 = no such family, or no such weight; no API
  key needed), the manager re-prompts once on a miss, and an unresolvable
  choice falls to the last link of the fallback chain. PowerPoint names one
  typeface per run and silently substitutes Calibri — the chain exists so that
  substitution is a decision, not an accident. `fontStack()` in
  `Agents/pptx/theme.ts` renders it for the web preview.
- `slideSize` and `source` on the StyleSpec are overwritten in code after
  parsing, and generated images are resized with Sharp to the exact pixel size
  requested. Dimensions are never left to a model — or to a template
  definition, which gets its canvas fixed by the same code on the same rule.
  `source.type` is `image` or `template`, and `source.path` is the file the
  analyzer read or the template id, respectively.
- Embeddings use `GENAI_EMBED_MODEL` at **1536 dimensions**, locked to the
  `vector(1536)` column; pgvector cannot HNSW-index more than 2000 dims.
  Changing the model or width needs a new migration *and* a full re-embed —
  mixed-model vectors return confident nonsense with no error.
- **Provider failures are retried and explained.** `callModel` and the image
  POST retry transient statuses (408/409/429/5xx and network faults) twice with
  a backoff, and never retry a 4xx that will fail identically forever. The
  thrown message carries the model, the HTTP status and the response body —
  OpenRouter's own "Provider returned error" says nothing on its own, and a
  deck is a dozen sequential calls, so one unexplained 429 used to kill a whole
  build.
- Record every call in `agent_runs` (model, tokens, cost, latency).
- **Watching a build.** Two views of the same thing. In the terminal, each run
  prints `[deck <id8>]` lines: `▶` start, `·` milestone, `✓` finished call
  (agent · model · tokens · cost · latency), `✗` failure, `→` one specialist
  handing to the next, and `~` the **model's own reasoning**, streamed as it
  arrives and indented under the stage that produced it. The reasoning is the
  point: this pipeline's failures are bad judgements, not exceptions, and a
  stack trace cannot show you why the designer talked itself into a 14-inch
  text box. `OPENROUTER_REASONING_EFFORT=minimal` turns it off along with the
  thinking itself. In the app, the deck
  card's **Agent activity** panel reads `agent_runs` back (`getAgentRunsAction`)
  and refreshes while the build is running. A failed deck is unhelpful without
  it — "Generation failed" does not say which specialist gave up, on what
  model, after how long.

## Conventions

- TypeScript strict. No `any` — use `unknown` and narrow.
- Data access lives in `src/lib/data/`; components receive data as props rather
  than fetching in a `useEffect`.
- Mutations are Server Actions or Route Handlers.
- Errors: throw with a message naming what failed. Do not swallow a `catch`.

## Before you say you are done

```bash
npm run typecheck
npm run lint
npm run build
npm run smoke            # deterministic half: skills, layout, pptx build+validate
clerk doctor             # after touching auth or env
```

Two smoke tests make real model calls and cost a few cents each, so run them
when you have touched what they cover rather than on every change:

- `npm run smoke:research` — the reasoning half: the Researcher with live
  search, the planner's word budgets, the locked style block. For changes to
  `Agent.ts`, `memory.ts`, `reasoning.ts`, `image-prompt.ts`.
- `npm run smoke:render` — **free and offline-ish**: builds a deck from
  hand-written specs covering every case that has broken before (a display
  heading too wide for its box, cards whose content is in `items`, type below
  the legible floor, a caption in a tight band), runs the real measuring,
  lifting and compaction passes, and writes both the .pptx and the
  `SlideCanvas` preview so the two can be compared by eye. No API key, no cost
  — run it on any change to the builder, the canvas, the layouts or the
  metrics.
- `npm run smoke:deck` — the whole pipeline end to end, then the web renderer.
  It prints the per-call cost of every stage and writes a `preview.html` you
  can open to see the deck exactly as `SlideCanvas` draws it in the app. This
  is the only test that proves the .pptx and the browser agree, so run it after
  any change to the Manager, the builder or the renderer.

All must pass. If you changed SQL, also confirm `npm run db:reset` completes
cleanly against the local stack.
